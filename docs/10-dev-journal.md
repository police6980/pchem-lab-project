## Phase 0 — 기획·설계 (2026-04-21 이전, 오프라인)

### 개요
프로젝트 범위·철학·하드웨어 선정·소프트웨어 아키텍처를
확정한 단계. 실제 코드 작성 전, Claude와의 장시간 대화를
통해 설계 문서 세트(`docs/00~05`)를 구축.

### 주요 의사결정

#### 결정 1: "2층 분리" 아키텍처 — 실측 레이어와 시뮬레이션 레이어의 엄격한 분리

**배경**: 센서 데이터를 받아 시뮬레이션에 반영하는 시스템을
설계할 때, "센서값을 시뮬레이션 변수에 직접 대입"하는
방식이 가장 단순하다. 그러나 이 방식은 교육적으로 위험하다.
학생이 시뮬레이션을 보고 "이것이 실제 기체가 움직이는
모습"으로 오해할 수 있기 때문이다.

**결정**: 실측값(센서 원시 데이터)을 별도 레이어로 분리하고,
시뮬레이션은 물리 법칙(이상기체 가정)에 따라 **스스로**
계산하도록 구성. 두 레이어를 UI상 병기하여 학생이 "이론이
예측하는 값 vs 실제 측정값"의 차이를 인지할 수 있게 한다.

**근거**:
- Johnstone(1991) 삼원 이론: 거시·미시·기호 세 차원의
  연결이 화학 학습의 핵심
- Chao 등(2016)의 sensor-augmented learning 연구:
  센서 데이터가 시뮬레이션과 "일치하지 않는 순간"이
  오히려 학습 기회가 된다는 관점
- 학생이 이상기체와 실제 기체의 차이(반데르발스 편차 등)를
  탐구할 수 있는 여지 확보

**배제된 대안**:
- 센서값을 시뮬레이션 변수에 직접 대입: 교육 목표 훼손
- 시뮬레이션만 사용(센서 없음): "실험"의 의미 상실

#### 결정 2: "인과 과정을 시간축에 펼친다" 원칙 — 선택적 시간 지연

**배경**: 학생이 피스톤을 누르면 압력이 즉각 변하고,
그에 따라 부피도 즉각 변해야 한다. 하지만 모든 것이 즉시
바뀌면 학생이 "왜 그렇게 되는가"의 과정을 포착하지 못한다.

**결정**: 물리량마다 수렴 시정수(tau)를 다르게 설정.
- 입자 속도(1차 물리량): tau=0.05s (거의 즉시)
- 박스 부피(2차 물리량): tau=0.5s (인과 과정을 보여줌)

**구현 공식**: `current += (target - current) * (dt / tau)`

**교육적 효과**: 학생이 피스톤을 누르는 순간 → 입자 밀도가
눈에 띄게 상승 → 입자-피스톤 충돌이 많아지는 모습 관찰 →
그 결과로 박스가 서서히 좁아짐. 거시 현상의 미시적 원인을
시간 순서대로 체감.

#### 결정 3: 2D 시뮬레이션 + "초기 대비 상대값" 표시

**배경**: 실제 기체는 3D이지만 3D 시뮬레이션은 개발 부담
(렌더링, 카메라 조작, 교실 환경 부적합)이 크다.

**결정**: p5.js 기반 2D 시뮬레이션. 2D와 3D 간의 물리량
단위 불일치 문제는 **모든 물리량을 "초기값 대비 상대값"
으로 표시**하여 회피.

**근거**:
- p5.js는 교육용 레퍼런스가 풍부
- 모든 입자가 화면에 가시화되는 것이 교육적으로 유리
- 2D의 통계적 요동 보상을 위해 입자 수 300~400개로 증가

#### 결정 4: 하드웨어는 ESP32 + DFRobot SEN0257 (보일 법칙)

**배경**: Arduino Uno와 ESP32 중 선택.

**결정**: ESP32. 근거:
- 3.3V 로직, 풍부한 ADC 채널
- 충분한 성능(Wi-Fi 확장 여지)
- 산염기(pH 캘리브레이션) 등 후속 실험에도 재사용 가능
- Uno와 가격 차이 미미

**배제된 대안**: Arduino Uno (5V/3.3V 혼재로 센서 연결 번거로움)

#### 결정 5: Git + GitHub, 구글드라이브 분리

**배경**: 여러 컴퓨터를 오가며 개발. 동기화 도구 선택.

**결정**: 코드는 Git(GitHub), 문서·실험데이터는 구글드라이브.
`node_modules`, `.git` 폴더는 구글드라이브 동기화에서 제외.

**근거**: 구글드라이브는 "최신 파일 하나"만 유지하는 구조라
Claude Code가 다중 파일을 수정할 때 동기화 충돌 위험이 크다.
Git은 명확한 충돌 처리와 이력 관리를 제공.

#### 결정: 안정화 윈도우 1s → 2s → 10s로 확장

**배경**: 초기엔 1초 윈도우로 안정화 판정. 하지만 압력
변경 직후 값이 요동치는 구간에서 부정확한 측정이 잡혔다.

**결정**: 최종적으로 10초 + 카운트다운 UI.

**근거**:
- 250ms 샘플링 주기 × 40회 = 10초 동안 P·V 편차가
  0.5% 이내로 유지되어야 "안정화됨"으로 판정
- 카운트다운 UI로 학생에게 "기다리는 중"임을 시각화

#### 결정: 유령 입자(ghost) 2700개 + 실입자 300개

**배경**: 2D 시뮬레이션의 통계적 요동이 커서 충돌/s 값이
매 프레임 널뛰었다.

**결정**: 화면에 보이는 실입자 300개 외에, 렌더링하지 않는
유령 입자 2700개를 별도로 시뮬레이션. 충돌/s는 전체(실+유령)
기준으로 계산.

**근거**: 통계 요동은 √N에 반비례. N을 10배 키우면 노이즈가
√10 ≈ 3배 감소. 렌더링 비용은 실입자만 발생하므로 FPS 영향 미미.

## Phase 2 — AI 튜터 통합·보고서·UX 완성 (2026-04-21 ~ 2026-04-22)

### 개요
MVP 시뮬레이터 위에 생성형 AI 튜터를 통합하고, 교육적 산출물(탐구 보고서

것이 아니라 "질문-성찰-피드백-재탐구"의 교육적 사이클을 구현한 것이 핵심.
총 4개 부속 Phase(Part 1~4)로 진행.

### 2026-04-21 — AI 튜터 UI 골격 (Phase 2-A Part 1~2)

#### 한 일
- 사이드바 레이아웃 확정 (우측 380px sticky)
- 탭 구조: Q1 / Q2 / Q3 / 자유 질문
- 대화형 메시지 렌더링 (user/assistant 말풍선)

#### 결정: 단발 피드백 → 대화형(multi-turn) 구조로 전환

**배경**: 초기 설계는 "학생이 성찰 답변 작성 → AI 한 번 피드백 → 끝"의 
단발 구조였음. 그러나 실제 영재 교육에서 중요한 건 AI가 "한 번 답해주고 
끝"이 아니라 "답을 보고 또 되묻는" 왕복 대화.

**결정**: 모든 Q(Q1/Q2/Q3/자유)에서 multi-turn 대화 지원. 
`messages` 배열을 누적해서 API에 전송하는 구조.

**근거**:
- 교육학적으로 메타인지·재사고 유도에는 왕복 대화가 필수
- 단발 구조에서는 학생이 AI 피드백에 "아 그렇군" 정도에서 멈춤
- 왕복이 있어야 학생이 답을 수정·확장하는 경험이 생김

**배제된 대안**: 단발 피드백 (구현은 단순하나 교육 효과 부족)

#### 결정: BYOK(Bring Your Own Key) + sessionStorage

**배경**: Anthropic API 키를 어떻게 관리할 것인가. 백엔드 서버를 세워서 
키를 숨기는 방식 vs 학생/교사가 직접 키 입력.

**결정**: BYOK 방식. API 키는 학생/교사가 직접 입력하고 `sessionStorage`에
만 저장. 탭 닫으면 삭제.

**근거**:
- 백엔드 서버 불필요 → 정적 호스팅(GitHub Pages)만으로 배포 가능
- 키 유출 시 책임 소재 명확
- 세션 종료 시 자동 삭제로 공용 컴퓨터에서 안전
- 교사가 자기 계정으로 비용 통제 가능

**배제된 대안**:
- 백엔드 프록시: 서버 운영 부담, 비용 집중
- localStorage 영구 저장: 공용 컴퓨터에서 키 유출 위험

### 2026-04-21 — 자유 질문 탭 (Phase 2-A Part 2.5)

#### 결정: 자유 질문 모드의 시스템 프롬프트 차별화

**배경**: Q1~Q3는 성찰 유도용이라 "답을 주지 말고 질문 확장" 원칙. 반면 
학생이 실험 도중 "이 색깔은 왜 이래요?" 같은 **학습 보조** 질문을 할 
공간도 필요.

**결정**: 자유 탭 전용 시스템 프롬프트 별도 작성. 답변 가능하되 400자 이내, 
마지막에 탐구 방향 한 문장 덧붙이기, 오개념은 실험으로 확인할 방법 제시.

#### 결정: 3영역(A·중앙·B) 모델 → 2영역(A → B 수용) 전환

**배경**: 초안 설계서(b831816)는 "주사기 A → 중앙 용기 → 주사기 B" 3영역 구조.
실제 실험 시 중앙 용기·피스톤 고정·연결 튜브의 구현 복잡도 과대. 교사 1인이
수업 중 관리 불가능 수준. 학생이 다뤄야 할 변수도 V_A/V_B/V_fixed 3개로 증가.

**결정**: 중앙 용기 제거. 주사기 A(능동, 피스톤 이동) → 주사기 B(수용, 피스톤 고정)
직접 연결 구조로 단순화. A→B 사이 체크밸브로 역류 방지. A 피스톤 끝까지 밀어
A의 모든 기체를 B로 이동. 주입 후 A는 비어있음 → UI에서 A 압력 "—" 비표시.

**근거**:
- 하드웨어 부품 수 감소 (중앙 용기 제거), 조달·조립 단순화
- 학생 조작 변수 축소 (V_fixed 삭제 → V_A, V_B 만)
- 돌턴 법칙 교육 효과는 유지 — `P_total = (V_A/V_B + 1) × 1 atm` 공식 성립
- 센서는 주사기 B 에만 부착 (1개 사용) → 실센서 모드 비용·배선 절감
- 초기 압력 = 대기압 1 atm 으로 A·B 동일. A 압력은 B 센서값 복사 표시 (결정 7)

**배제된 대안**:

#### 진단 — A 박스 입자 잔여 (d4b6979)

**증상**: A → B 주입 시 가끔 (간헐적) A 박스 입자가 분출 안 됨. 피스톤 따라 내려옴. 5~10 회 중 1 회.

#### 진단 — R5 박스 입자 stuck (72403ca)

**증상**: B 박스 (R5) 왼쪽 / 오른쪽 벽 boundary 근처에 입자 몇 개가 거의 안 움직임 (시각상 정지). 다른 입자는 정상 운동.
