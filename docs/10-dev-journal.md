## Phase 0 — 기획·설계 (2026-04-20 이전)

### 개요
프로젝트 범위·철학·하드웨어 선정·소프트웨어 아키텍처를
확정한 단계. 실제 코드 작성 전, Claude와의 장시간 대화를
통해 설계 문서 세트(`docs/00~05`)를 구축.

### 주요 의사결정

#### 결정 1: "2층 분리" 아키텍처 — 실측 레이어와 시뮬레이션 레이어의 엄격한 분리

**배경**: 센서 데이터를 받아 시뮬레이션에 반영하는 시스템을
설계할 때, "센서값을 시뮬레이션 변수에 직접 대입"하는
방식이 가장 단순하다. 그러나 이 방식은 교육적으로 위험하다.
학생이 시뮬레이션을 보고 "이것이 실제 기체가 움직이는
모습"으로 오해할 수 있기 때문이다.

**결정**: 실측값(센서 원시 데이터)을 별도 레이어로 분리하고,
시뮬레이션은 물리 법칙(이상기체 가정)에 따라 **스스로**
계산하도록 구성. 두 레이어를 UI상 병기하여 학생이 "이론이
예측하는 값 vs 실제 측정값"의 차이를 인지할 수 있게 한다.

**근거**:
- Johnstone(1991) 삼원 이론: 거시·미시·기호 세 차원의
  연결이 화학 학습의 핵심
- Chao 등(2016)의 sensor-augmented learning 연구:
  센서 데이터가 시뮬레이션과 "일치하지 않는 순간"이
  오히려 학습 기회가 된다는 관점
- 학생이 이상기체와 실제 기체의 차이(반데르발스 편차 등)를
  탐구할 수 있는 여지 확보

**배제된 대안**:
- 센서값을 시뮬레이션 변수에 직접 대입: 교육 목표 훼손
- 시뮬레이션만 사용(센서 없음): "실험"의 의미 상실

#### 결정 2: "인과 과정을 시간축에 펼친다" 원칙 — 선택적 시간 지연

**배경**: 학생이 피스톤을 누르면 압력이 즉각 변하고,
그에 따라 부피도 즉각 변해야 한다. 하지만 모든 것이 즉시
바뀌면 학생이 "왜 그렇게 되는가"의 과정을 포착하지 못한다.

**결정**: 물리량마다 수렴 시정수(tau)를 다르게 설정.
- 입자 속도(1차 물리량): tau=0.05s (거의 즉시)
- 박스 부피(2차 물리량): tau=0.5s (인과 과정을 보여줌)

**구현 공식**: `current += (target - current) * (dt / tau)`

**교육적 효과**: 학생이 피스톤을 누르는 순간 → 입자 밀도가
눈에 띄게 상승 → 입자-피스톤 충돌이 많아지는 모습 관찰 →
그 결과로 박스가 서서히 좁아짐. 거시 현상의 미시적 원인을
시간 순서대로 체감.

#### 결정 3: 2D 시뮬레이션 + "초기 대비 상대값" 표시

**배경**: 실제 기체는 3D이지만 3D 시뮬레이션은 개발 부담
(렌더링, 카메라 조작, 교실 환경 부적합)이 크다.

**결정**: p5.js 기반 2D 시뮬레이션. 2D와 3D 간의 물리량
단위 불일치 문제는 **모든 물리량을 "초기값 대비 상대값"
으로 표시**하여 회피.

**근거**:
- p5.js는 교육용 레퍼런스가 풍부
- 모든 입자가 화면에 가시화되는 것이 교육적으로 유리
- 2D의 통계적 요동 보상을 위해 입자 수 300~400개로 증가

#### 결정 4: 하드웨어는 ESP32 + DFRobot SEN0257 (보일 법칙)

**배경**: Arduino Uno와 ESP32 중 선택.

**결정**: ESP32. 근거:
- 3.3V 로직, 풍부한 ADC 채널
- 충분한 성능(Wi-Fi 확장 여지)
- 산염기(pH 캘리브레이션) 등 후속 실험에도 재사용 가능
- Uno와 가격 차이 미미

**배제된 대안**: Arduino Uno (5V/3.3V 혼재로 센서 연결 번거로움)

#### 결정 5: Git + GitHub, 구글드라이브 분리

**배경**: 여러 컴퓨터를 오가며 개발. 동기화 도구 선택.

**결정**: 코드는 Git(GitHub), 문서·실험데이터는 구글드라이브.
`node_modules`, `.git` 폴더는 구글드라이브 동기화에서 제외.

**근거**: 구글드라이브는 "최신 파일 하나"만 유지하는 구조라
Claude Code가 다중 파일을 수정할 때 동기화 충돌 위험이 크다.
Git은 명확한 충돌 처리와 이력 관리를 제공.

- 충돌 섬광 효과 (운동량 비례, 0.1~0.15초 페이드)
- 속도 히스토그램 UI
- DEV MODE 압력 슬라이더 (개발 편의용)

#### 결정: 피스톤 전용 충돌 카운트

**배경**: "충돌/s"를 UI에 표시할 때, 전체 벽의 충돌을 셀지
피스톤 면만 셀지 결정 필요.

**결정**: 피스톤 면 충돌만 카운트.

**근거**:
1. 실제 센서(DFRobot SEN0257)가 피스톤 위치에 대응
2. 학생 멘탈 모델("손에 밀리는 힘")과 일치
3. 평형 상태에서는 모든 벽이 같은 압력이므로 물리적으로 등가
4. 피스톤 면적이 변하지 않아 계산이 단순
5. 샤를 법칙으로 확장할 때 벽 면적 변동 복잡성 회피

### 2026-04-21 — 측정·기록·차트 시스템

#### 한 일
- 안정화 감지 알고리즘 (슬라이딩 윈도우 + 임계값 0.5%)
- [기록] 버튼 + 이동평균 저장
- 측정 테이블 (P, V, P·V, v̄, 충돌/s 컬럼)
- P vs V 산점도 + 보일 법칙 이론 곡선
- 온도 조절 슬라이더 (프리셋 + 커스텀)
- V_baseline 자동 재계산 (샤를 법칙 암묵 적용)
- 입자 속도 √(T_new/T_old) 스케일링
- CSV 다운로드 2종 (측정점 CSV, 연속 로그 CSV)

#### 결정: 안정화 윈도우 1s → 2s → 10s로 확장

**배경**: 초기엔 1초 윈도우로 안정화 판정. 하지만 압력
변경 직후 값이 요동치는 구간에서 부정확한 측정이 잡혔다.

**결정**: 최종적으로 10초 + 카운트다운 UI.

**근거**:
- 250ms 샘플링 주기 × 40회 = 10초 동안 P·V 편차가
  0.5% 이내로 유지되어야 "안정화됨"으로 판정
- 카운트다운 UI로 학생에게 "기다리는 중"임을 시각화

#### 결정: 유령 입자(ghost) 2700개 + 실입자 300개

**배경**: 2D 시뮬레이션의 통계적 요동이 커서 충돌/s 값이
매 프레임 널뛰었다.

**결정**: 화면에 보이는 실입자 300개 외에, 렌더링하지 않는
유령 입자 2700개를 별도로 시뮬레이션. 충돌/s는 전체(실+유령)
기준으로 계산.

**근거**: 통계 요동은 √N에 반비례. N을 10배 키우면 노이즈가
√10 ≈ 3배 감소. 렌더링 비용은 실입자만 발생하므로 FPS 영향 미미.

### 2026-04-21 — 물리 정확성 검증

#### 교육적 의미
물리적으로 정확한 시뮬레이션은 학생이 "가짜 애니메이션"이 아닌
"실제 물리 법칙의 결과"로 인식하게 만든다. 이 검증 기록이
있어야 학생·교사·연구자 모두에게 신뢰 가능한 교구가 된다.
